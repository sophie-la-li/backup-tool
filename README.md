# Backup Tool

> **Acknowledgment:** This tool was planned and directed by a human, but the code itself was
> mostly generated by [Claude Code](https://claude.com/claude-code).

Self-contained `rclone`-based backup utility, supporting multiple backup destinations at once.
No dependency on `~/.config/rclone/rclone.conf`, no secrets in the repo — everything sensitive
lives in the system keyring (`secret-tool`) and a temporary rclone config is generated at
runtime and removed on exit.

Every destination is the same shape: a **base** target (where the bytes actually live — an
SFTP account, a local/mounted directory, ...) plus a **backup** target layered on top of it via
rclone `crypt`, so what's stored on the base is always encrypted.

## Dependencies

- `rclone` >= 1.75 (for `--sftp-pin-host-key` host key pinning, only needed by `sftp`-type
  destinations)
- `secret-tool` (libsecret / GNOME Keyring)
- `mktemp`, `sed` (standard on any Linux system)

## Setup

1. Create a destination by copying the example:

   ```sh
   cp -r destinations/_example destinations/<name>
   mv destinations/<name>/config.sh.template destinations/<name>/config.sh
   ```

   Edit `destinations/<name>/config.sh`:

   - `BASE_TYPE` — `sftp` (e.g. a Hetzner StorageBox) or `local` (a local or already-mounted
     directory, e.g. a USB drive or NAS mount).
   - Fill in the fields under whichever `BASE_TYPE` section you chose; the other section is
     unused and can be left alone or deleted.
   - `BACKUP_PATH`, `LOCAL_BACKUP_DIR`, and the VFS mount options apply regardless of type.

   `config.sh` contains no secrets and is safe to commit — it's specific to this one
   destination, so each `destinations/<name>/config.sh` is its own file.

2. Make it the active destination:

   ```sh
   ./script.sh destinations-use <name>
   ```

3. Run:

   ```sh
   ./script.sh secrets-init
   ```

   For an `sftp`-type destination you'll be prompted for the SFTP password, the crypt
   password, and a crypt salt (password2); a `local`-type destination skips the SFTP
   password since there's nothing to authenticate to. Stored values go in the system keyring
   under the `backup-tool` app, namespaced per destination.

   The SFTP password (sftp only) is mandatory. The crypt password and salt can both be
   left blank:

   - Leaving the **crypt password** blank means you don't want it in the keyring — you'll be
     prompted for it interactively every time a command needs it (mount/sync).
   - Leaving the **crypt salt** blank means you don't use one — that's remembered permanently,
     so you won't be asked for it again on future runs.

4. Check what's stored at any time with:

   ```sh
   ./script.sh secrets-show
   ```

   Each secret shows as `stored` (value present), `skipped` (explicitly left blank — won't be
   asked for again), or `missing` (never configured — will be prompted for on next use). Values
   themselves are never printed.

5. For `sftp`-type destinations, the first time you connect you'll be shown the SFTP server's
   SSH host key fingerprint (via rclone's `--sftp-pin-host-key`) and asked to trust it. Once
   accepted, it's pinned to `destinations/<name>/host_key` and every later connection is
   verified against that pinned key — no per-run warning, and no silent skip of host key
   checking either. If the server's host key ever legitimately changes, delete that file to
   re-pin. `local`-type destinations skip this step entirely (there's no SSH connection).

## Multiple destinations

```sh
./script.sh destinations-list        # show configured destinations, * marks the active one
./script.sh destinations-use <name>  # switch the active destination
```

Every other command below operates on whichever destination is currently active. Each
destination has its own config, its own namespaced secrets, its own mount points (by default
`mounts/<name>/base`, `mounts/<name>/backup` — overridable per destination via `BASE_MOUNT`/
`BACKUP_MOUNT` in its `config.sh`), and (for `sftp` types) its own pinned host key — nothing is
shared between destinations except the `script.sh` logic itself.

## Usage

```sh
./script.sh destinations-list         # list configured destinations (* marks the active one)
./script.sh destinations-use <name>   # switch the active destination
./script.sh remote-mount              # mount the base target (unencrypted) for browsing
./script.sh remote-backup-mount       # mount the encrypted backup target
./script.sh remote-backup-sync-dry    # preview what a sync would change
./script.sh remote-backup-sync        # sync LOCAL_BACKUP_DIR to the encrypted backup target
./script.sh secrets-init              # interactively store secrets for the active destination
./script.sh secrets-show              # show which secrets are stored (never prints values)
./script.sh secrets-delete            # remove stored secrets for the active destination
./script.sh help
```

Mounts run in the foreground; press Ctrl+C to unmount. Sync deletes files on the destination
that no longer exist locally, exactly as `rclone sync` normally does — use `remote-backup-sync-dry`
first if you're unsure.

GNOME/GIO-based file managers (Nautilus, Nemo, ...) tend to only show a mount in their sidebar
automatically when `BASE_MOUNT`/`BACKUP_MOUNT` is under your home directory — mounting elsewhere
(e.g. `/mnt/...`) loses that convenience. There's no portable fix for this: rclone can pass
`-o`/`--option` hints (like `x-gvfs-show`) straight to the FUSE backend to get around it, but
that passthrough only works when rclone was built with the cgo/libfuse `cmount` backend —
distro-packaged builds (e.g. Mint's apt package) are often built without it and error on any
`-o`/`--option` flag, so it's not used here.

`remote-backup-mount` writes go through a local write-back cache (`VFS_CACHE_MODE`/
`VFS_WRITE_BACK` in the destination's `config.sh`) before being uploaded — if the mount is
killed uncleanly (crash, `kill -9`, power loss) mid-write, the destination can end up with a
truncated file. `config.sh` sets `VFS_WRITE_BACK` low (1s vs rclone's 5s default) to shrink that
window, but it can't close it entirely. For actual backups, prefer `remote-backup-sync`, which
uploads each file in one shot and isn't exposed to this risk — treat the mount as a
browsing/inspection tool.

## How it works

For every command that touches a destination, `script.sh`:

1. Resolves the active destination (`current_destination`) and sources its `config.sh`.
2. Looks up whatever secrets that destination's `BASE_TYPE` needs, plus the crypt password and
   salt, in `secret-tool` (prompting and optionally storing them if missing).
3. For `sftp`-type destinations, verifies the SFTP server's SSH host key against the pinned
   entry in `destinations/<name>/host_key` (prompting to pin it on first connection).
4. Renders `templates/base-$BASE_TYPE.conf.template` + `templates/backup.conf.template` (the
   crypt layer, always the same regardless of base type) into a `mktemp` temporary directory,
   obscuring secrets with `rclone obscure` along the way.
5. Runs `rclone --config <temp-config> ...`.
6. Removes the temporary directory on exit via `trap`.

Nothing is ever written to disk unobscured, and the temporary config never touches the
repository or your global rclone config. `host_key` isn't a secret (SSH host keys are public)
but is specific to that destination, so you may want to keep `destinations/*/host_key` and
`current_destination` out of version control if this project is later put under git —
`destinations/*/config.sh` (as opposed to `config.sh.template`) is worth keeping local too,
since it's a per-machine/per-instance file (see Setup step 1).

## Extending

Adding a new base type (B2, S3, NAS, ...) means:

1. A new `templates/base-<type>.conf.template` with that backend's rclone config fields.
2. A case branch in `generate_config()` (`script.sh`) that renders it — mirroring the existing
   `sftp`/`local` branches.
3. If the type needs host key pinning or other one-time trust setup, extend
   `base_needs_host_key_pinning()`; if it needs secrets beyond the crypt password/salt, extend
   `collect_secrets`/`secrets_init`/`secrets_show`/`secrets_delete` the same way the `sftp`
   password is handled there today.
4. A new `BASE_TYPE=<type>` section documented in `destinations/_example/config.sh.template`.

The `backup` (crypt) target, the mount/sync logic (`mount_remote`/`sync_remote`), and the
destination-switching mechanism are all shared and don't need to change.
